# qhyc 远端部署手册（腾讯云轻量服务器）

> 配套文件：`docker-compose.cloud.yml`
> 本文只讲「怎么搬过去且跑起来」，不包含业务功能说明。

---

## 0. 为什么要单独一份编排

本地 `docker-compose.yml` 通过 bind mount 把三类**宿主机路径**挂进容器：

| 挂载 | 宿主机路径 | 远端后果 |
|---|---|---|
| `${WB_PIPELINE_PATH}` | `C:/Users/Seven/.workbuddy/skills/.../scripts` | Docker **静默建空目录**，决策链路（简报/研究/基本面/监控/信号）无源码可执行，且不报错 |
| `${QH_BRIEF_PATH}` | `E:/QH/期货简报` | 同上，简报产出落进容器内部，宿主看不到、重启即丢 |
| `./app ./scripts ./web/dist` | 项目源码 | 远端只推镜像时这些空目录会**覆盖镜像内的真实代码**，容器启动即崩 |

`docker-compose.cloud.yml` 的做法：**源码全部内化进镜像**，只挂运行时产物（logs / runtime / qh / imports / pgdata）。

---

## 1. 服务器规格建议

| 项 | 建议 | 理由 |
|---|---|---|
| 内存 | **≥ 4 GB**（2 GB 会 OOM） | 数据库 37 GB，`shared_buffers` 默认按 `TS_TUNE_MEMORY` 算；2 GB 机器上 PostgreSQL + api + scheduler + pipeline 四个进程极易被 OOM killer 杀掉 |
| 磁盘 | **≥ 100 GB 数据盘** | pgdata 约 37 GB，系统盘放不下；务必挂数据盘 |
| CPU | ≥ 2 核 | 合成/回测为 CPU 密集 |
| 端口 | 只开 8000（或走 Nginx 反代 443） | **5432 绝不对公网开放**：cloud 版已 `listen_addresses=localhost` 且不映射宿主端口 |

## 2. 开发机：构建与推送

### 2.1 内化 WB 决策链路源码（**必须先做**）

```bash
python scripts/vendor_pipeline_src.py          # 生成 vendor/pipeline_src
python scripts/vendor_pipeline_src.py --check  # 校验与源一致
```

不做这一步，`docker build` 会在 `COPY vendor/pipeline_src` 处失败。
WB 源码更新后需重跑本脚本并重新构建镜像。

### 2.2 构建镜像

```bash
# 腾讯云容器镜像服务（CCR）
docker build -t ccr.ccs.tencentyun.com/<namespace>/qhyc:20260924 .
docker push ccr.ccs.tencentyun.com/<namespace>/qhyc:20260924
```

> 若服务器不便配镜像仓库，也可用离线方式：
> `docker save qhyc:20260924 | gzip > qhyc.tar.gz` → 上传 → `docker load -i qhyc.tar.gz`。
> 注意镜像含 torch（CPU 版），体积较大。

## 3. 数据迁移（37 GB，最耗时的一步）

```bash
# 开发机：导出（容器需停止写入，或先 docker compose stop）
docker exec qhyc-timescaledb pg_dump -U futures -d futures -Fc -f /tmp/futures.dump
docker cp qhyc-timescaledb:/tmp/futures.dump ./futures.dump

# 服务器：先起数据库，再导入
docker compose -f docker-compose.cloud.yml up -d timescaledb
docker cp ./futures.dump qhyc-timescaledb:/tmp/futures.dump
docker exec qhyc-timescaledb pg_restore -U futures -d futures -j 2 /tmp/futures.dump
```

**替代方案（推荐评估）**：远端只保留策略需要的品种与年份（如 2015 年至今的 50 个主力连续）。
分钟线 1.37 亿行里，2005–2014 年段对策略几乎无贡献，剔掉可把库压到 1/3 以下，
迁移时间和磁盘压力都会显著下降。

## 4. 服务器：启动

```bash
# 4.1 准备目录与配置
git clone <repo> qhyc && cd qhyc
cp .env.example .env
vi .env                      # 至少改 POSTGRES_PASSWORD / 推送 token 等

# 4.2 启动（不映射 5432 到宿主）
export QHYC_IMAGE=ccr.ccs.tencentyun.com/<namespace>/qhyc:20260924
docker compose -f docker-compose.cloud.yml up -d

# 4.3 看状态
docker compose -f docker-compose.cloud.yml ps
docker logs -f qhyc-api
```

> `.env` 需要包含 api/scheduler/pipeline 的全部密钥。若 `env_file` 缺项，
> 容器会以空值启动（不会报错），表现为推送/采集静默失败。

## 5. 上线验证清单

按此顺序逐项确认，任一项不通过即未就绪：

| # | 检查 | 命令 / 判据 |
|---|---|---|
| 1 | API 健康 | `curl -s localhost:8000/health` → `{"status":"ok"}` |
| 2 | 路由齐全 | `curl -s localhost:8000/openapi.json \| python -c "import sys,json;print(len(json.load(sys.stdin)['paths']))"` |
| 3 | 数据到位 | 抽查 `futures_symbol`、`daily_bar` 行数与开发机一致 |
| 4 | **快照补丁生效** | `curl -s localhost:8000/pipeline/status` → `base_patch_applied: true`、`manifest_match: true` |
| 5 | 简报产出路径正确 | `docker exec qhyc-pipeline ls /app/qh` → 有 `简报内容/` 等，**不应出现名为 `E:` 的目录** |
| 6 | 无宿主路径残留 | `docker exec qhyc-api ls /app/pipeline_src` → 应有 `run_pipeline.py` 与 `pipeline/` |
| 7 | 调度在跑 | `docker logs qhyc-scheduler` 有 `fusion_scan` / 采集日志 |
| 8 | 5432 未外露 | `nmap -p 5432 <公网IP>` → closed |

### 关于第 4、5 项（本次已修复的缺陷）

旧逻辑 `ensure_snapshot()` **只在快照目录为空时**才同步源码，导致：
一旦建立过快照，`_patch_base()` 对已有快照永不执行 → `run_pipeline.py` 里
`BASE = r"E:/QH/期货简报"` 在 Linux 下被当成相对路径 → 产出写到
`/app/runtime/pipeline_snapshot/E:/QH/...` 垃圾目录，宿主简报不更新。

现改为 `snapshots.needs_resync()` 做漂移检测（补丁缺失 / 文件集合变化 / 内容变化 → 重建），
修复后 `base_patch_applied` 已由 `false` 变为 `true`。

## 6. 已知限制与后续项

1. **`config/local.yaml` 的 `imports.source_root` 仍是 `E:/Docker/qhyc/imports`**
   仅供宿主机侧参考；容器内走 `container_root: /app/imports`。云端已挂空卷，
   目录存在但无历史数据 —— 依赖本地导入文件的功能（如 `local_importer`）在远端无米下锅。
   如需该功能，要么同步 imports 目录，要么改用远端采集。

2. **数据库时区语义**：`fut_kline` 的时间戳存储存在 +8 小时偏移（序列顺序正确，
   不影响回测），但跨库比对时间窗时需统一减 8 小时。

3. **torch 层**：Dockerfile 固定尝试安装 CPU 版 torch，拉取失败会跳过（LSTM 自动禁用）。
   云端构建若网络不通会拖慢构建，可按需注释该层。

4. **pgdata 37 GB**：建议在第 3 步做取舍，并配置定期备份（腾讯云快照或 `pg_dump` 定时任务）。
