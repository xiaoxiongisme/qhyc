## 三、L0/L1/L2 分层核对 —— 你的架构方向对，但现状有 3 处偏离

你的理解：**L0（1m）后复权 → L1（5/15/30/60m）由 L0 合成 → 日线采集并后复权**，三层一致。

| 层 | 你的设计 | 实际实现 | 一致？ |
|---|---|---|---|
| **L0** | 1m **后复权** | 1m **前复权**（`adjust_minute.py`：`cum[i]=Σ_{k>i}` 锚定最新段） | ❌ **方向相反** |
| **L1** | 由 L0 合成 | `bar_5m/15m/30m/60m` **独立采集**（各自 KQ.m@ 源），非由 L0 合成；后复权靠 `roll_segment` 运行时套用 | ⚠️ **路径不同** |
| **L2 日线** | 采集 + 后复权 | `daily_bar`(4源，未复权) + `fut_kline daily`(continuous，未复权)；**无后复权日线** | ❌ **缺后复权** |

### 三处缺口

| # | 缺口 | 影响 |
|---|---|---|
| **A** | **L0 是前复权** | 与"后复权唯一口径"直接冲突；且前复权"每次换月需全历史重写"，`adjust_minute.py` 增量模式每次对换月品种全量重算 → 云端 5,862 万行表的维护成本来源 |
| **B** | **L1 非由 L0 合成，而是独立采集 + 运行时套偏移** | 省了 L0→L1 聚合开销，但**L0/L1 换月检测必须一致**才敢混用。`adjust_minute.py` 注释已说明该设计（1m 振幅太小检不准，用 15m 双门检测定位换月）——**合理，但一致性依赖"共用 15m 检测器"这一约定，而非结构性保证** |
| **C** | **日线无后复权** | `roll_segment` 只覆盖 min5/15/30/60，**无 daily/hourly** → 日线/小时线回测只能用 continuous |

### 结论

> **你的架构方向是对的（后复权 + 分层一致），但完全对齐需一次口径重构**：
> ①L0 改后复权（重写 `adjust_minute.py`）②`roll_segment` 补 daily/hourly 覆盖
> ③先解决 `build_roll_segments` 从未调度的问题。
> **工程量较大，建议单独立项，不夹在本次清理里。**

## 五、★ 方法论：超表删除必须分批 + 在 DB 端执行

### 踩坑过程

| 尝试 | 方式 | 结果 |
|---|---|---|
| 1 | `deprecate_cont_adj.py --action delete --confirm`（单条 `DELETE ... WHERE kind=ANY`） | **SIGTERM 超时，0 行删除** |
| 2 | 改为逐 freq 分批 + 前台跑 | **仍 SIGTERM，0 行删除** |
| 3 | **在容器内用 `docker exec -d` 跑 DB 端 DO 块** | ✅ **成功，341.5s 删完 994 万行** |

### 两个关键教训

**① 前台超时会回滚整个事务。** 进程被杀 → 未提交事务自动回滚 → 库内零进展。
不是"删得慢"，是"删了但没生效"。**验收必须查库，不能只看脚本是否跑过。**

**② 612-chunk 超表上不要写单条跨全表 DELETE。** 项目脚本自己的注释已给出正解：

```python
# 刻意**不用**一次性 `GROUP BY freq` 全表扫：fut_kline 是 612 个 chunk 的超表，
# 单条聚合要一次锁住全部 chunk（实测在有其他写入并发时会被拖到分钟级超时）。
# 按 freq 拆开后每条都能走 `(freq,kind,symbol,trade_datetime)` 主键裁剪。
```

**分批实测耗时**：daily 5.8s / hourly 48.6s / min15 150.6s / min30 94.3s / min60 42.2s = **341.5s**。

已将分批逻辑固化进 `scripts/deprecate_cont_adj.py`（含 `import time` 与
`cur.execute(...)` 后单独 `fetchall()` 的写法修正 —— **psycopg2 的 `execute` 返回 None，不能链式**）。
