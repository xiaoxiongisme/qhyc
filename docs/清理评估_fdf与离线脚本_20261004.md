# 天勤 清理评估（fdf 模块 + 离线脚本 + fut_kline ETL）

> 评估日期：2026-10-04。评估人：WB（工程复审）。
> 目标：判断「继续推进 fdf + 离线脚本的 天勤 清理以达 `grep 天勤 → 0`」是否应作为独立专项、是否需先做数据覆盖评估、以及 fut_kline ETL 的 akshare 替代方案是否成立。
> 方法：全仓 `grep 天勤` 枚举（51 文件）+ 逐文件引用性质分类 + `fut_kline` 消费者静态追踪 + 容器内 DB 直查。

---

## 0. 结论（先行）

**用户建议「作为独立专项、先评估数据覆盖再动手」方向正确，但范围须修正：**

- **fut_kline ETL 不需要 akshare 替代方案，应直接退役（decommission）。** 实测 `fut_kline` 表在 G9（迁移 027）后已全面孤儿化：`continuous`/`cont_adj` 两个 kind 正式退役；唯一存活的 `kind='contract'` **仅被已退役的 `adjust_fdf` 读取**（生成 cont_adj），无任何活跃生产代码消费 `fut_kline`。容器内直查：`fut_kline` 在 **2026-10-01 之后 0 行**（天勤 增量链路实际已停写）。
- **真正仍需 akshare 替代 天勤 的「活」依赖只有 2 个文件**：`app/ingest/hourly_collector.py` 与 `app/ingest/minute_collector.py`（即既有 C9 范围，受 T4 +8h 时区修复门槛约束）。其余 49 个 天勤 引用要么是 fdf 模块本身（随退役一并删除）、要么是离线一次性脚本（可删/可改 akshare）、要么是**注释/列名/数据源标签字符串**（无 API 调用，擦除即可）。
- 因此「独立专项」应拆成两条并行线：**线一 = fut_kline/fdf 退役（删，不做替代）；线二 = 活采集器 C9 akshare 化（T4 前置）**。覆盖评估只需确认线二，线一靠「零活读者」证据即可放行。

## 2. 关键发现：fut_kline 已全面孤儿化（退役而非替代的硬证据）

**2.1 迁移层（迁移 027_retire_fut_kline_continuous.sql）**
- 声明 `fut_kline.kind ∈ {contract(原始), continuous(已废弃派生,2026-10-04 G9 退役,不再刷新), cont_adj(已退役前复权)}`。
- 处置为「加法式」：不 DROP、不删存量，但 `rebuild_fut_kline.py` 默认 `--kinds` 改为仅 `contract`；caliber 路由的 `continuous` 改指 `daily_bar`/`hourly_bar`（L0 原始主连）。
- 存量 9.9M 行标 orphan，可后续显式 purge。

**2.2 消费者静态追踪**
- `load_contract_frames`（读 `kind='contract'`）仅 2 处调用：`app/ingest/fdf/adjust_fdf.py:220`（生成 cont_adj → 已退役）、`app/ingest/fdf/_diag.py`（诊断）。
- `build_roll_segments.py` 读 `bar_5m/bar_15m/bar_30m/bar_60m`（L0 原始），**不读 fut_kline**；后复权/换月管线与 fut_kline 无关。
- 生产代码（backtest/features/strategies/routers/scheduler 除 `_fut_kline_job` 外）对 `fut_kline` 的引用仅为：config 类、`FutKline` 模型、`contract_code.py` 的 sym 映射、`ops` 备份列名——**均无数据读取**。

**2.3 容器内 DB 直查（权威）**
```
fut_kline rows after 2026-10-01 (post-G9): []     ← 全表 2026-10-01 后 0 行
fut_kline.contract total rows: (百万级存量，但不再刷新)
```
→ 天勤 增量作业 `_fut_kline_job`（scheduler.py:875，跑 `ingest_fut_kline_incremental.py` → `fetch_fdf.run()`）**当前未产出任何新数据**，`fut_kline` 处于冻结态。退役它不产生任何功能损失。

## 3. 数据覆盖评估（对用户「先评估覆盖」的回应）

| 数据需求 | 天勤 提供 | akshare 是否可覆盖 | 结论 |
|---|---|---|---|
| **活增量分钟/小时/日线（连续主连）** | `fetch_fdf` / `_fetch_天勤` | `futures_zh_minute_sina(period=1/15/60)`、`get_czce_daily`、`futures_main_sina`+`futures_rule` 日历 | ✅ 可覆盖（即 C9，受 T4 +8h 门槛约束） |
| **逐合约历史分钟/小时 K 线** | `get_kline_data_series`（唯一源） | ❌ akshare 仅连续主连（`futures_main_sina`），无逐合约历史分钟序列；CZCE 仅日线 | **缺口，但无影响**——`fut_kline.contract` 已孤儿化，无任何活读者 |
| **合约代码解析 `天勤_symbol` 列** | `contract_code_map.天勤_symbol` | 非数据，是符号翻译元数据；akshare/sina 用 4 位标准码即可 | 删列 + 去 `to_天勤`（C9 范畴） |
| **双源比对 / 脏数据校验** | 已删（T7），由 `resilience.py` 单源校验替代 | 已由 akshare_source 单源韧性层覆盖 | ✅ 已覆盖 |

**覆盖结论**：akshare 对「活数据」全覆盖（C9 已规划）；所谓「fut_kline ETL 的 akshare 替代」是伪命题——因为该 ETL 的产物（逐合约历史 + 前复权连续）均已退役，替代它只会造出一套新的孤儿数据。正确动作是**删**。

## 4. 风险与动手前须验证项

- **R1（线一放行前提）**：静态已证零活读者，但 DELETE 前须再跑一次 `deploy_gate` 级 grep + 运行时 import 烟雾测试（启动 qhyc-api，确认无模块因删 fdf 而 import 失败）。⚠ `app/ingest/orchestrator.py`、`contract_code.py`、`symbol_code.py`、`barstore.py` 若 `import` 了 fdf 子模块，删 fdf 会拖垮它们——须先解除这些 import（见 §5 线一）。
- **R2（线二 T4 前置）**：C9 删 天勤 前必须先修 T4（§6.6），否则启用 akshare 分支会把 +8h 偏移棒入库造未来函数，且未修就删 天勤 会让活采集归零。
- **R3（表保留 vs 删除）**：建议先「停写+停读」（删 fdf/作业/config、清引用），`fut_kline` 表按 027 留 orphan 不 DROP，观察 N 日无异常再显式 purge。避免一次删库风险。
- **R4（离线脚本回填能力）**：若未来需重灌历史（DB 损毁/迁移），3 个离线脚本是唯一切口。删除前确认有 akshare 版回填方案或接受「历史回填暂不可」。

## 5. 推荐专项结构（覆盖优先，分阶段可独立验收）

### 线一：fut_kline / fdf 退役（删除，非替代）
1. **解除 import 依赖**：`orchestrator.py`/`contract_code.py`/`symbol_code.py`/`barstore.py` 中 `from app.ingest.fdf import ...` 全部移除（改为标准码 4 位解析，不依赖天勤原生码）。
2. **删调度与配置**：`scheduler.py` 移除 `_fut_kline_job` 注册；`config.py` 删 `FutKlineConfig`/`FutKlineRebuildConfig` 及 `fut_kline`/`fut_kline_rebuild` 字段。
3. **删 fdf 模块**：`app/ingest/fdf/` 整目录删除；`scripts/rebuild_fut_kline.py`、`scripts/ingest_fut_kline_incremental.py` 删除。
4. **删/改离线脚本（C 类）**：3 个 `backfill_*`/`fetch_contract_1min` 删除或改写为 akshare（R4 决策）。
5. **模型与表**：`models/domain.py` `FutKline` 模型保留（表 orphan 不 DROP）或随 purge 移除；`migrations` 补 `028_purge_fut_kline.sql`（观察期后执行）。
6. **验收**：`grep -rn "from app.ingest.fdf\|import fdf" app scripts` → 0；qhyc-api 冷启动无 import 错；`deploy_gate` 通过。

### 线二：活采集器 C9 akshare 化（既有范围，T4 前置）
- 见 `PRD改造落地执行方案_CB直接执行版_20261004.md` §4 + §6.6。仅 2 文件，akshare 全覆盖。

### 线三：元数据擦除（达 `grep 天勤 → 0`）
- `contract_code_map.天勤_symbol` 列 + `to_天勤()` + `routers/symbols.py` 暴露字段 + `features/pipeline.py`/`fusion_signal.py`/`fusion_backtest.py`/`orchestrator.py`/`data_selfcheck.py` 中 `src="天勤"`/`akshare_天勤` 标签 + 各 docstring 注释中的 "天勤" → 重命名为 `src="akshare"` 或删除。
- **验收**：`grep -rn "天勤" app scripts` → 0（注释/文档说明除外，须显式标注）。

## 6. 给用户的两项拍板

1. **fut_kline 处置**：采纳「退役（删 fdf + 停作业 + 留 orphan 表）」而非「akshare 重建」。理由见 §2/§3。
2. **离线回填脚本**：保留 akshare 版回填能力（推荐，低代价）还是直接删除接受「历史回填暂不可」（若云库 15432 为权威且已备份，可删）。

> 注：本评估未改动任何代码，符合「评估后交 CB 执行」边界。覆盖评估结论（线一靠零读者证据、线二 akshare 已规划）支持「先评估再动手」的专项方式，但明确 fut_kline 替代方案不成立。
