## 0. 如何使用本文档

- **执行环境**：所有 DB/脚本操作在 `qhyc-api` 或 `qhyc-scheduler` 容器内执行，统一前缀：
  ```bash
  docker exec -w /app -e PYTHONPATH=/app qhyc-api  python <脚本> [参数]
  docker exec -w /app -e PYTHONPATH=/app qhyc-scheduler python <脚本> [参数]
  ```
- **数据库**：`qhyc-timescaledb`（宿主机 5432，与容器内同库）。`spot_basis` 等源表在本地库已存在且新鲜（见 §1）。
- **符号约定**：`qhyc-api` 用于即席查询/写库；`qhyc-scheduler` 用于跑调度类脚本（与运行时同源）。写库前务必先 `--dry-run` 或在事务外小范围验证。
- **云库**：`seed_follow_rule` / `infer_main_contract` 需要**全量** `contract_daily` 才能标注全部 84 品种；本地库仅含部分品种近 3 月数据（见 §1 C2）。**完整 84 品种标注须在云库（15432，需恢复 SSH 隧道后）运行**；本地运行只能标注可判定子集。
- **铁律**：任何"代码↔库一致"修复完成后，必须跑 §10 对应验收命令确认，禁止"看起来改了"。

### C8 `roll_segment` 缺 daily/hourly（daily/hourly back_adj 静默回退 continuous）
- **代码事实**：`caliber.default_caliber_for(freq)` 对无 `roll_segment` 段的周期显式回退 `"continuous"` 并 `logger.warning`（非静默）。`build_roll_segments.py` 的 `TABLE`/`FREQ_MIN` 仅含 `min5/15/30/60`，**不支持 daily/hourly**。
- **库事实**：`roll_segment` 仅 4 个分钟频。
- **影响**：`BarStore.load("FG","daily","back_adj")` → 抛 `CaliberError`（无路由）；但 `default_caliber_for("daily")` → 返回 `continuous`（raw）。即"显式 back_adj"报错、"默认"却静默用 raw——**两种取数路径行为不一致**。日线/小时线回测无后复权 offset 可用。
- **【WB 机理校正】后复权不是"落在一根 K 线"；方案 A 下日线≠5 分钟**：
  - 误区：后复权 `cum_offset(k) = -Σ_{j≤k} delta_j`（`build_roll_segments.py:265`，锚定最早段、最早段偏移恒为 0）是**全历史累积平移**——一根半年前的 bar 会被其后每次换月跳空**累加**偏移，越古老偏移越大、最近为 0。**不是"某一根 K 线被点修正"**。
  - 边界对应恒等式：**仅对同口径成立**。两事实：① raw 聚合恒等式——日线是 5 分钟同源 888 聚合，故 `日线开盘=首根5m开盘`、`日线收盘=末根5m收盘`（恒真）；② 后复权 offset 是**纯日历时间函数、与周期无关**——换月点来自 `main_contract_map.change_flag`（日期级，`:89-111`），同一笔换月 gap 在所有周期减同一常量（`:233` "用锚点 gap，非本 freq 的 cc"）。⇒ **若日线和 5 分钟同为后复权（方案 B），则后复权日线收盘=后复权5m收盘精确相等**。
  - **方案 A 下不成立**：A 让 `日线=raw(offset=0)`、`5分钟=back_adj(offset=cum_offset)`，两者差一个累积偏移 `cum_offset(D)≠0`（D 之前发生过换月即非零）。故**方案 A 里"日线收盘=5分钟收盘"是错的**——差的就是累积跳空。任意"日线(raw) 与 5m(back_adj) 混算"都会引入恒定偏置，是 caliber 违例。
  - 推论：本直觉反而论证**方案 B 能完美对齐**，但 B 当前被阻塞（见 §C8.1 + §10）。
- **修复（二选一，CB 拍板）**：
  - **方案 A（推荐，范围小）**：明确"日线/小时线维持 continuous（未复权）基准"，在 `caliber.py` 文档与 PRD 标注此决策；`build_roll_segments` 暂不扩展。回测日线/小时线用 raw 连续价（换月跳空已知）。
  - **方案 B（完整）**：扩展 `build_roll_segments.py` 支持 `--freqs daily,hourly`（新增 `daily_bar`/`hourly_bar` → `roll_segment` 段映射），再跑 `python scripts/build_roll_segments.py --freqs daily,hourly`。

### C8.1 回测-实盘一致性保证边界（禁混用口径能否保证"回测≈实盘"？）

**结论先讲**：禁混用口径 + 消 default 静默坑是**必要条件，远非充分条件**。"回测与实盘相差不大"靠的是一整套执行真实性与防前视纪律，caliber 一致性只消除了其中**一类**偏差（研究价 vs 执行价的拼接错位）。即使口径完全对齐，回测仍可能与实盘差很大。

- **caliber 一致性消除的偏差（唯一一类）**：研究/因子用的价格序列与实盘下单反解所用的 888 连续价，因换月拼接方式不同而产生的**点位系统性错位**。方案 A + 单口径纪律把它清零。
- **caliber 一致性消除不了的偏差（须另行治理，否则回测≈实盘不成立）**：
  1. **执行真实性与成本建模**：回测通常假设"信号 bar 收盘或次 bar 开盘成交、全额成交、零拒单"；实盘有下单延迟、队列位置、部分成交、限价单未成交/拒单、交易所费率与保证金变动。须用真实滑点+手续费+部分成交模型的回测引擎。
  2. **前视偏差（lookahead）**：`T4/R7` +8h 时区坑（sina 标签偏移）——若回测 naive 用时间戳切 session，会把次交易日数据算进当日信号。信号只能用**决策时点之前**的数据；时间戳须先对齐时区再回测。
  3. **换月成交成本建模**：回测假设换月收盘瞬时切换、无价差成本；实盘换月有买卖价差+真实跳空。且若回测用 `back_adj`（OI 主力 `roll_segment`，现有 `contract_at` 读 `underlying`）而实盘执行近月 `inferred_symbol`（丙丁 §4.3 冲突），**合约与成本本就不同**——这恰是 caliber 之外的"合约口径"错位，需 §4.3 路径 A/B 拍板后才能对齐。
  4. **流动性（R2）**：近月临交割 OI 骤降、价差放大；回测假设恒定流动性→实盘滑点放大。需近月剩余交易日<N 护栏（见 §4.5）。
  5. **过拟合（偏差最大头，与口径无关）**：参数 in-sample 优化过拟合。须过既有评审四道否决——①半样本换参（前半最优→后半符号相反即毙）；②去 TOP5 贡献品种（OOS 由盈转亏即毙）；③纯 OOS 参数面符号一致率（<50% 即毙）；④参数高原（OOS 正收益格子占比）。成本通常非死因，过拟合才是。
  6. **市场冲击 / 限价单 GTC 行为 / 断线重连**：大单移动价格、隔夜单取消规则、CTP/QMT 断线恢复——回测默认无。
  7. **P0-2 实盘通道未建（最硬约束）**：现网 `app/execution` 缺 `router/position_manager/broker_http/stop_loss/persistence/scheduler/monitor` 七模块、`ctp-gateway`/`qhyc-bridge` 不存在（见 §3 P0-2）。**当前根本没有实盘通路，无法跑"回测 vs 实盘"对照**——须先按 §3 建 P0-2（SimNow→模拟账户→实盘），用 shadow/paper 交易实测真实 gap，才能谈"相差不大"。
- **落地要求**：① caliber 单口径纪律（本 §C8 + CI 断言）；② 回测引擎补真实滑点/手续费/部分成交（B8/B9 双轨"显式展期成本"须覆盖近月频度）；③ T4/R7 时区前视审计；④ 丙丁 §4.3 合约口径拍板；⑤ R2 近月护栏；⑥ 既有四道过拟合否决门禁（评审纪律）；⑦ P0-2 shadow 实测。七项缺一，回测≈实盘无保证。

## 6.6 时区前视（T4/R7）落地细则 —— 数据层 PRD §6.6 补强

> **本节能独立执行，无需翻数据层 PRD。**它是 C9（去天勤）的**前置硬门槛**（见 §2 C9、§4）：T4 不修就启用 akshare 分支，会把 +8h 偏移棒入库，回测直接造出未来函数；且未修 T4 就删 天勤 会让行情入库全盘 0 行。
> **机理已现网实测复核**，代码事实来自 `app/ingest/hourly_collector.py`、`app/ingest/minute_collector.py`、`app/core/db.py`。

### 6.6.1 成因：为什么会产生 +8h 前视（两步，均在 ingest）

**第 1 步 —— sina 接口标签本身已偏移 +8h（接口侧毛病）**
`HourlyCollector.__init__` 注释（hourly_collector.py:124-128）原话：新浪分钟线 `datetime` 标签整体 +8h——真实 09:00–10:00 的收盘棒被标成 `"18:00"`、夜盘 22:00–01:00 被标成 `"6:00–9:00"`。这是新浪把"收盘时刻"按某个口径错标，不是本地时区转换问题。

**第 2 步 —— 解析器未校正，直接当成真实上海时间存库（代码侧毛病）**
`_parse_ak_dt`（hourly_collector.py:50-70）拿到字符串 `"2025-12-26 18:00:00"` 后只做：
```python
dt = dt.replace(tzinfo=_SH_TZ)          # 把 "18:00" 当真实上海时间
return dt.astimezone(timezone.utc)
```
于是真实 10:00 上海收盘的棒，被存成 **18:00 上海 = 10:00 UTC**；而真实瞬时是 **02:00 UTC**。**每条棒被持久化到未来 8 小时。**
- **关键陷阱：偏移量不统一。**数据层 PRD §6.6 明示"日盘/夜盘偏移量不一致，须精确测量，不能假设统一 −8h"（日盘 09:00→18:00 经实测是 +9h 疑点，夜盘是 +8h）。所以时间戳排序被搅乱、跨交易日错配，不是简单地整体平移能还原。

### 6.6.2 怎么变成"未来函数"（泄漏路径 A/B/C）

回测/信号按**时间戳顺序**消费 bar，并用时间戳归属交易日（`cfg_trading_session` 窗口规则：21:00–23:00 这类夜盘归属**次日**）。错标后：

- **路径 A（主泄漏）**：真实日盘 13:00–15:00 的棒被存成 21:00–23:00 → 正好落入"夜盘窗口" → 被归属到**次日交易日 T+1**。回测算"T 日收盘信号"时，就把本属 T+1 的棒当成 T 日已发生的数据用 → **未来函数**。
- **路径 B（对称）**：真实夜盘 T（21:00–23:00，按规则本属 T+1）被存成次日 05:00–07:00 → 落在凌晨，被归回 T 日。两向都让相邻交易日的棒互相串。
- **路径 C（打穿新鲜度门禁）**：+8h 的"未来棒"经 as-of 查询/新鲜度判断时，因其时间戳已"越过现在"，状态机在错位序列上误触发——这正是 PRD 记录的事故（单轮 18 信号、SN414170/AP7332.5 推送用户盘面上找不到标记）。

> **重要事实**：当前 sina 分支**已禁用**——`_fetch_akshare` 返回 `[]`（hourly_collector.py:195-210），且 `_valid_hourly_ts`（hourly_collector.py:105-117）因 18 点不在合法整点集合 `{0,1,2,9,10,11,13,14,15,21,22,23}` 直接丢弃这些棒。所以现网回测跑的是 天勤 派生数据（`_parse_tq_dt` 用真实 epoch，时间戳正确），**未被中毒**。但这只是"没启用"，不是"已修复"——T4 没修就启用 akshare 分支必然复发。

