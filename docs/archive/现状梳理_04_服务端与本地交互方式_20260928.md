# 现状梳理 04 · 服务端（云端）与本地的交互方式

> 盘点时间：2026-09-28 ｜ 盘点人：WorkBuddy
> 依据：`docker-compose.cloud.yml`、`scripts/sync_*.py`、`app/scheduler.py` 的 `CLOUD_SYNC_ENABLED` 分支、实测连接
> ⚠️ 本次只能通过 SSH 隧道 `127.0.0.1:15432` 访问云端数据库，**无法确认云端容器的运行状态**（需你在服务器上 `docker ps` 复核）

---

## 0. 先看结论（4 条）

1. **真正的生产库是云端库**。本地 `docker-compose.yml` 里 `DATABASE_URL` 指向 `host.docker.internal:15432`（云端隧道），而代码里 `DATABASE_URL` 优先于 `POSTGRES_HOST` → **本地容器写的也是云端库**。本地 `5432` 那个库实质是"研究/备份副本"。
   ⚠️ **勘误 2026-10-01**：compose 现已不含 `DATABASE_URL`，本地容器实测写**本地库**（82 品种补采全部落本地）；详见 00 文档 P0-3 勘误。
2. **两端能力不对等**：分钟线（1m / 5m）与 `fut_kline` 的 min15/30/60 `continuous` **只在云端**；`spot_basis`、`member_position_rank` 云端也远比本地全。本地反而独有 `sync_state`、`fusion_signal_log`。
3. **交互有 6 条通道**（SSH 隧道 / 同步脚本 / 裸机直连 / docker exec / 镜像推送 / 容器内打补丁），其中"容器内打补丁"是非正规通道，应废弃。
4. **存在双跑风险**：本地 `qhyc-scheduler`（Up）与云端 `qhyc-scheduler` 若同时运行，会**对同一个云端库执行同一批定时任务**（含 fusion_scan 推送）→ 重复写、重复推。这一条必须尽快核实。

## 2. 六条交互通道

| # | 通道 | 机制 | 正规性 | 用途 |
|:--:|---|---|:--:|---|
| 1 | **SSH 端口转发** | `ssh -L 15432:timescaledb:5432 <user>@<cloud-host>` | ✅ | 本地访问云端库的唯一通道（所有 `sync_*`、`_cloud_*` 脚本的前提） |
| 2 | **表级同步脚本** | `sync_cloud_local.py`(311行，双向/幂等/整表快照+增量，水位记 `sync_state`)、`sync_bar15m_server.py`、`sync_factor_value_server.py`、`sync_fundamentals_server.py` | ✅ | 云↔地数据搬运（双 psycopg2 连接分块 COPY） |
| 3 | **裸机脚本直连云库** | 如本轮 `python runtime/_adjust_bars.py --freq min15 --port 15432` | ⚠️ | 绕过容器直接写云端；有效但不可复现（脚本不在镜像里） |
| 4 | **docker exec 进容器跑 CLI** | `docker compose exec api python scripts/xxx.py` | ✅ | 手动触发采集/回测/训练 |
| 5 | **镜像推送发布** | `QHYC_IMAGE=ccr.ccs.tencentyun.com/<ns>/qhyc:<tag>` → 云端 `docker compose -f docker-compose.cloud.yml up -d` | ✅ | 代码发布的正规路径 |
| 6 | **容器内打补丁** | `_patch_minute.py` / `_patch_minute2.py` / `_patch_inventory.py` 直接改云端容器内源码 | ❌ **废弃** | 应急热修；导致云端代码与 git 分叉 |

## 3. 同步机制细节

### 3.1 `sync_cloud_local.py`（统一云地同步链路）

- 连接：云端 = `127.0.0.1:15432`（隧道），本地 = 本地库。
- 能力：**双向**、幂等、整表快照 + 增量。
- 涉及表：`bar_15m`、`bar_30m`、`daily_bar`、`factor_value` + 水位表 `sync_state`。
- 触发：由 `app/scheduler.py` 的 `_sync_cloud_local_job` 以 **subprocess 隔离**方式调用（03:15）。
- **裸机专用模式**：当 `CLOUD_SYNC_ENABLED=1` 时，`_build_scheduler()` **只注册 `cloud_local_sync` 一个作业并立即返回**，其余采集/训练/回测全部交给云端调度器。注释明确说明原因：裸机上 `POSTGRES_HOST=timescaledb`（docker 服务名）不可解析，且要避免与云端重复执行。

> ⚠️ 但本地 `docker-compose.yml` **没有设** `CLOUD_SYNC_ENABLED=1`，所以本地 `qhyc-scheduler` 容器注册的是**全部任务** —— 与云端调度器职责重叠。见 §4。

### 3.2 同步覆盖范围（实测缺口）

`sync_cloud_local.py` 只覆盖 `bar_15m / bar_30m / daily_bar / factor_value` 四张表（外加 `sync_bar15m_server.py` 覆盖 bar_15/30/60m）。**未覆盖**：`minute_bar*`、`bar_5m`、`fut_kline`、`member_position_rank*`、`spot_basis`、`warehouse_receipt`、`inventory`、`roll_yield`。

→ 这直接解释了 §1 中"本地缺 1 分钟 / 5 分钟 / fut_kline 分钟级 continuous"的现状。

## 4. ⚠️ 双跑风险（必须核实）

```
云端 qhyc-scheduler ──┐
                      ├──▶ 同一个云端库 futures
本地 qhyc-scheduler ──┘    （本地 DATABASE_URL=host.docker.internal:15432）
```

若两端 scheduler 同时 `Up`：

| 作业 | 后果 |
|---|---|
| `fusion_scan`（:05/:35） | **重复扫描 + 重复推送**（手机收到两条相同信号） |
| `ingest_*`（每日三档） | 重复采集（幂等 upsert，数据无害但浪费） |
| `hourly_collect`（每小时） | 同上 |
| `minute_and_bars`（每 30 分钟） | 重复合成（合成作业是"尾删再重建"，**并发会互相破坏**） |
| `adjust_*` / `rebuild_fut_kline` | 重复复权/重建 |
| `task_run` / `prediction_result` | 双份流水 |

本轮已实测到一个相关现象：云端 `bar_*` 合成作业会**周期性"尾删再重建"**，我跑 min30 复权的 7 分钟里源尾部正好被删 → 产出缺 5 天的 cont_adj（见 01 号文档 §5）。若两端合成作业并发，这类竞态会更频繁。

**建议核实与处置**：
1. 在服务器执行 `docker ps --format "table {{.Names}}\t{{.Status}}"` 确认云端容器状态。
2. 若两端都跑 → 本地 compose 的 scheduler 必须设 `CLOUD_SYNC_ENABLED=1`（只做同步），或本地直接 `docker compose stop scheduler`。
