# 口径与数据问题修复方案（2026-10-03）

> 用户要求：给出可落地建议，避免口径和实际偏差，避免数据（采集/构建/使用/回测）出问题。
> **本方案基于实测数据，不是原则性建议。每条都附验证判据。**

---

## 一、★ 先说最重要的发现：后复权方案本身有数学缺陷

用户设想「后复权是唯一口径，L0 生成后复权、L1 由 L0 合成、L2 日线也后复权」。
**我按这个设想做了可行性验证，结论是：后复权在期货上无法直接成立。**

### 实测证据（84 品种 min15）

`roll_segment.cum_offset` 跨度（max−min）：

| 指标 | 值 |
|---|---|
| 中位 | 1,563 点 |
| 最大 | **20,050 点（SN888）** |
| RU888 跨度 | 20,005 点（min −17,955） |

套到价格上后：

| 品种 | 首价 | 最低价 | min(cum_offset) | **后复权后最低价** | 需抬升 | 占首价 |
|---|---|---|---|---|---|---|
| **RU888** | 13,470 | 9,360 | −17,955 | **−8,595** | 8,595 | **63.8%** |
| CJ888 | — | 7,560 | −14,355 | −6,795 | 6,795 | — |
| LH888 | — | 9,000 | −12,250 | −3,250 | 3,250 | — |
| FB888 | 61.3 | 0 | −2,681.6 | −2,681.6 | 2,681.6 | 4,374% |
| JD888 | 4,286 | 2,639 | −4,372 | −1,733 | 1,733 | 40.4% |
| WR888 | 2,941 | 0 | −1,118 | −1,118 | 1,118 | 38.0% |

**后复权后最低价 ≤0 的品种：12/84（14%）**

### 根因：期货不是永续正价序列

| | 股票 | 期货 |
|---|---|---|
| 长期价格趋势 | 总体向上（分红/盈利驱动） | **可跌到 1/3**（RU888 首价 13,470 → 最低 9,360） |
| 全序列平移 | 后复权天然成立 | 累积偏移必然溢出为负 |

> **这不是实现 bug，是数学必然。** 前复权压早期价、后复权压后期价，
> 任何"全序列一次性平移"的方案在期货上都会产生负价格。

### 但断层又不能不管

| 指标 | 值 |
|---|---|
| 换月断层（>3×日内 ATR 的跳空）占比 | **中位 1.415%**、平均 1.968%（79 品种 min15） |
| 单根最大跳空 | **中位 11.17%**、最大 1315% |
| ATR 失真（加法平移） | **0%**（中位比值 1.0000，78/83 在 ±1% 内） |

1.4% 的断层占比远高于 0.1% 的可忽略门槛 —— **断层必须处理**。
而加法平移对 ATR 是零失真的 —— **说明平移方向是对的，只是锚点选错了**。

## 二、四条出路（按推荐度）

### ★ 出路一（推荐）：连续序列 + 换月段标记，不做全序列平移

**核心思想**：价格保持真实不动，只把"换月点"标记出来，让引擎在换月处**重置 ATR / 止损基准**。

| 维度 | 说明 |
|---|---|
| 改动范围 | 只改引擎的 ATR 计算，**不动任何价格数据** |
| 实现 | `roll_segment.roll_ts` 已有换月时刻（2,911 段/84 品种）；在 ATR14/EMA 的窗口里，把跨越换月点的 bar 排除或降权 |
| 副作用 | **零**。价格真实、点数真实、ATR 只在换月处有微小口径变化 |
| 成本 | 引擎改 ~30 行 + 一致性测试 |
| 缺点 | 换月点前后的 ATR 仍有轻微口径变化（非严格连续） |

**这是唯一无副作用的方案。** 它把问题从"价格是否真实"转移到"指标是否连续"，后者容易正确处理。

### 出路二：后复权 + `price_shift`，接受早期点数失真

| 维度 | 说明 |
|---|---|
| 做法 | 启用 `apply_positivity`（`price_shift` 列至今**全为 0，从未启用**），整序列常量抬升使最低价 > 0 |
| 需抬升 | 11 个品种，中位 1,733 点、**占首价 38%**；RU888 需抬 8,595 点（64%） |
| 副作用 | **早期段"点数"失真 38%** → 2×ATR 止损 / 0.5×ATR 保本全靠点数 ⇒ 早期段信号全部偏移 |
| 结论 | **不推荐**。用 38% 的失真换取"不断层"，代价大于收益 |

### 出路三：只回测剔除负价品种的子集

| 维度 | 说明 |
|---|---|
| 做法 | 72/84 品种后复权后仍为正，回测限定在这 72 个 |
| 缺点 | 样本缩窄 **14%**（RU/CJ/LH/FB/JD/WR/RS/RR/BU/BB/CY/BC 被剔除），且**这批恰是螺纹/铁矿/农产品等主力** |
| 结论 | **不推荐**。剔掉的恰是高流动性品种，回测结论会失真 |

### 出路四：维持现状（未复权），显式承认断层

| 维度 | 说明 |
|---|---|
| 做法 | 保持 `continuous` 不变，在报告里注明"换月点 ATR 存在 1.4% 断层影响" |
| 成本 | 零 |
| 缺点 | 换月点的止损/ATR 基准偏差留在结果里，无法量化 |
| 结论 | 作为**临时兜底**可接受，不宜长期 |

## 三、★ P0 修复项（与复权方案无关，独立成立）

### P0-1：`fut_kline.adj` 全为假值 `0.0000`

**事实**：
```
column_name | data_type | column_default | is_nullable
adj         | numeric   | 0              | YES
```
| freq | kind | min(adj) | max(adj) | distinct |
|---|---|---|---|---|
| daily/hourly/min15/min30/min60 | continuous / contract | 0.0000 | 0.0000 | **1** |

**从未有过 True 值**（8 个 freq×kind 组合 distinct 全 = 1）。

**危害**：PRD §4.3.5 第 2 条说"回测只取 `adj=True`" → 任何按 `WHERE adj=true` 过滤的回测**取到 0 行且不报错**。

**修复（推荐 A，代价最小）**：

| 方案 | 动作 | 代价 |
|---|---|---|
| **A（推荐）** | **作废 `adj` 列语义**，改文档为"`adj` 列已废弃，复权口径由 `kind` 决定" | 零代码，立即生效 |
| B | 改 DDL 为 `boolean` 并回填 `kind='cont_adj'` → True | 1,600 万行 UPDATE + 改 `rebuild_fut_kline.py` 插入逻辑；**且 cont_adj 已删，该方案失去意义** |

> 既然 cont_adj 已退役，**A 是唯一合理选择**。建议在 `caliber.py` 加一条 fail-loud 断言：取数时若发现 `adj` 列为 numeric 则拒绝执行。

### P0-2：`build_roll_segments` 从未被调度

**事实**：`app/scheduler.py` 中 `roll_segment` 出现 **0 次**；`build_roll_segments` **零注册**。

**修复**（若选出路二或需要 roll_segment 作为换月标记源，则必须做）：

```python
# app/scheduler.py 建议新增（04:20，排在 bar_* 刷新之后、05:00 重建之前）
def _build_roll_segments_job() -> None:
    """构建/更新 roll_segment 换月分段表（back_adj 与换月标记的唯一数据源）。"""
    script = Path(__file__).resolve().parents[1] / "scripts" / "build_roll_segments.py"
    if not script.exists():
        logger.error("[scheduler] 找不到 roll_segment 构建脚本 %s", script)
        return
    # fail-loud：脚本存在但静默不跑 = roll_segment 停更（曾发生）
    ...
    sched.add_job(
        _build_roll_segments_job,
        trigger=CronTrigger(hour=4, minute=20, timezone=settings.env.TZ),
        id="build_roll_segments",
        replace_existing=True, max_instances=1, coalesce=True, misfire_grace_time=3600,
    )
```

**配套**：加**新鲜度守卫**（避免再次静默停更）——
```sql
SELECT max(seg_end) FROM roll_segment;   -- 应接近 max(bucket) FROM bar_15m
-- 差 > 3 天则 ERROR，禁止继续跑下游
```

## 四、数据链路的四道防线（防"采集/构建/使用/回测"出问题）

### 防线 1：采集层 —— 坏 bar 立刻拒收

`continuous` 有 9 根 `low=0`（O/H/C 正常），hourly 7 根、daily 0 根。

**修复建议**（不直接改价，先查上游是否有真值）：
```sql
-- 体检脚本加入 CI：任何 low<=0 或 high<max(open,close) 的 bar 计数
SELECT freq, symbol, count(*) FROM fut_kline
WHERE low <= 0 OR high < GREATEST(open, close) OR low > LEAST(open, close)
GROUP BY 1,2;
```
若 `main_continuous` 里有真实 low，回填；否则用 `low = LEAST(open, close)` 并**标记为 `src='derived'`**（与实测值可区分）。

### 防线 2：构建层 —— 换月点必须被标记

无论最终选哪条复权出路，**`roll_segment` 都应该是一张"活的"表**（出路一用它做换月标记，出路二用它算后复权）。

- 注册 `build_roll_segments` 调度（P0-2）
- 加新鲜度守卫
- 覆盖从 min5/15/30/60 **扩展到 daily/hourly**（当前缺失，导致这两个周期无法做后复权）

### 防线 3：使用层 —— 禁止裸 SQL，统一走 BarStore

`caliber.py` 文件头已写明"禁止裸 SQL"，但实测 `accept_v34.py` 自己就在写裸 SQL 读 `kind='continuous'`。

**建议**：
- 短期：给 `caliber.py` 加 `assert` 型体检入口，任何直接 SQL 取 K 线的地方改为 `BarStore`
- 长期：把 `accept_v34.py` 改走 BarStore（它是我的基线来源，改动会影响可复现性，需同步台账）

### 防线 4：回测层 —— 产物必须带口径四元组

PRD §14 第 2 条已要求 `(freq, kind, src, caliber)` 标注，但实测未落实。

**建议**：`backtest_result` 表已有 `caliber` 列（实测存在），关键是**强制写入**：
```python
# 回测入口统一封装
def run_backtest(strategy_id: str, freq: str, kind: str, src: str) -> BacktestResult:
    assert not pd.isna(kind), "口径未声明 —— 禁止回测"
    # ...
    save_result(..., caliber=Caliber(freq=freq, kind=kind, src=src, version=CALIBER_VERSION))
```

**fail-loud 清单（可直接做成启动自检）**：

| 检查 | 失败后果 |
|---|---|
| `DEFAULT_CALIBER` 对应的 roll_segment 有数据 | back_adj 静默空转（**已发生**） |
| `roll_segment.max(seg_end)` 与 `bar_*.max(bucket)` 差 < 3 天 | 分段表静默停更（**已发生**） |
| `fut_kline.adj` 若为 numeric 类型 | 按 `adj=true` 取数得 0 行（**已发生**） |
| 品种符号命名空间匹配（`KQ.m@EX.PROD` vs `XXX888`） | 跨口径 join 静默少数据（**已发生**） |
| `min(low) > 0` | 负价格流入 ATR/止损（**已发生**） |
| 时间列 tz 一致（`bucket` tz-naive vs `roll_ts` tz-aware） | 比较抛 TypeError（**本轮实测遇到**） |

**两轮验证都踩到的坑**：
- `bar_*.bucket` 是 **tz-naive**，`roll_segment.*` 是 **tz-aware(UTC)** → 直接比较抛 TypeError。
  **这意味着 `app/data/back_adjust.py` 在真实调用时也会踩这个坑**，建议在 `load_segments` 里统一 tz 处理。
- `roll_segment.roll_ts` 首个段为 `NaT`（无换月点），直接 `np.datetime64(NaT)` 会报错。
