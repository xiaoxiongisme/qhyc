### 2.1 导入与合成（本地）
- 脚本：`scripts/load_1min.py`
  - 读取 `D:/学习资料/期货主力连续1min最新`、`D:/学习资料/期货商品指数1min最新` 的 CSV。
  - 写入本地 `minute_bar`（默认连 `127.0.0.1:5432`，即 `qhyc-timescaledb`）。
  - 级联合成 `bar_5m ← 分钟`、`bar_15m ← 5m`、`bar_30m ← 15m`、`bar_60m ← 30m`（`_synth_symbol` 级联路径）。
  - 结论：**当年本地 `minute_bar` 确有约 1.14 亿行**，5/15/30/60m 也齐全。
- git：`8e7aab0 新增1分钟合约采集脚本 + 合成边界修复`、`7c0af17 fix(fetch): 1分钟数据分批入库规避PG 65535参数上限`。

### 2.2 迁移云端
- 脚本：`scripts/sync_bar15m_server.py`
  - 通过 `ssh -L 15432:timescaledb:5432 <user>@<cloud-host>` 隧道，把**本地表 COPY 到云端**。
  - **关键限制**：`DDL` 字典只含 `bar_15m / bar_30m / bar_60m`（第 30–52 行），**不含 `minute_bar` 和 `bar_5m`**。
  - 即：云端仅收到 15/30/60m；`minute_bar`、`bar_5m` 从未被该脚本同步到云端。
- git：`941b7ae feat: 信号落库 + 启动推送去重 + 云端运维脚本`、`ece2b99 feat: 移植准备——WB源码内化 + 云端编排 + 部署手册`。

### 2.3 ⚠️ 根因：本地 1m/5m 被显式清空
- 脚本：`scripts/fetch_contract_1min.py`
  - 第 144–148 行 `prune_1m_5m()`：`TRUNCATE TABLE minute_bar; TRUNCATE TABLE bar_5m;`（注释："本地清理：清空 1 分钟 / 5 分钟数据，保留表，留待按需重建"）。
  - 第 453 行 CLI 开关 `--prune-1m-5m` 直接触发该清空。
- **结论**：本地 `minute_bar`/`bar_5m` 是在某次"本地清理"中被 `TRUNCATE` 的，并非数据丢失。
  - 源 CSV 仍在 `D:/学习资料`，可随时重灌恢复。
  - 这也解释了当前本地实测：
    - `minute_bar = 0`、`bar_5m = 0`（被 prune）
    - `bar_15m = 8,845,980`、`bar_30m = 4,874,488`、`bar_60m = 2,862,892`（保留）
    - 基本面表（inventory / member_position_rank / warehouse_receipt / spot_basis 等）保留
    - `daily_bar = 167,507`（此表独立于 1m/5m，需另行核对是否完整）
