# 现状梳理 06 · 六层解耦迁移建议

> 制定时间：2026-09-28 ｜ 制定人：WorkBuddy
> 目标分层：**采集层 → 数据层 → 因子层 → 回测层 → 策略层 → 应用层**
> 输入：01（数据库）/ 02（脚本）/ 03（容器）/ 04（云地交互）/ 05（三方差异）

---

## 0. 先看结论

当前系统**不是分层架构，而是"数据库为中心的放射状架构"**：所有模块（采集、特征、预测、回测、策略、API）都直接写 SQL 连同一批表，彼此通过表隐式耦合。这解释了为什么"改一个地方会影响另一个看起来无关的地方"。

**解耦的核心动作只有一个**：在策略层/回测层/因子层与数据库之间插入一个**显式的"数据层接口（BarStore / FundamentalsStore）"**，禁止上层直接写 SQL 取行情。其余分层都是这一个动作的展开。

## 1. 六层的目标定义与边界

```
┌─────────────────────────────────────────────────────────────┐
│  L6 应用层   web(React) + FastAPI + notify(pushplus)          │
│              职责：展示预测/看板/回测报告、信号推送、任务编排    │
│              ❌ 禁止：算信号、算因子、直接写行情表              │
└───────────────────────────▲─────────────────────────────────┘
                            │ 只读接口
┌───────────────────────────┴─────────────────────────────────┐
│  L5 策略层   fusion_signal(V3.4) / 未来的 A 隐秘数轴          │
│              职责：方向/入场/止损/加码/离场 → 目标持仓          │
│              ✅ 单一真源：实时与回测共用同一信号循环            │
│              ❌ 禁止：读数据库、读因子表（只接收已注入的数据）  │
└───────────────────────────▲─────────────────────────────────┘
                            │ 信号事件流

│              职责：信号回放、成本模型、稳健性套件、walk-forward  │
│              ❌ 禁止：修改策略逻辑（只能调用）                  │
└───────┬───────────────────────────▲─────────────────────────┘
        │                           │
┌───────▼───────────────────────────┴─────────────────────────┐
│  L3 因子层   factor_registry / factor_value / asof_join       │
│              职责：注册、计算、asof 对齐(lag)、标准化、IC 评估  │

                            │
┌───────────────────────────┴─────────────────────────────────┐
│  L2 数据层   ★新增★ BarStore / FundamentalsStore              │
│              职责：存储 + 代码归一 + 合成 + 复权 + 日历         │
│                    + 质量门控 + 口径注册表                     │

│              输出：口径明确的 DataFrame（continuous/cont_adj）  │

                            │
┌───────────────────────────┴─────────────────────────────────┐
│  L1 采集层   akshare / tqsdk / Scrapling / 交易所官方          │
│              职责：抓取、限流、重试、断点、写 raw               │

```

| 层 | 输入 | 输出 | 唯一允许写的表 |
|---|---|---|---|
| L1 采集 | 外部数据源 | raw 行情 / 基本面 | `minute_bar`、`fut_kline(contract)`、基本面原始表 |
| L2 数据 | raw | 口径明确的 K 线/基本面 | `bar_*`、`minute_bar_adj`、`fut_kline(continuous/cont_adj)`、`daily_bar`、`hourly_bar`、`main_continuous`、`contract_code_map`、`trade_calendar`、`anomaly_ticket` |
| L3 因子 | L2 输出 + 基本面 | 因子值 | `factor_value`、`factor_registry` |
| L4 回测 | L2 输出 + L5 信号 + L3 因子 | 回测报告 | `backtest_result`、`backtest_detail`、`model_weights` |
| L5 策略 | L2 输出（注入）+ L3 因子（注入） | 目标持仓/信号事件 | `fusion_position` |
| L6 应用 | 各层只读接口 | 页面 / 推送 / 编排 | `prediction_result`、`fusion_push_log`、`fusion_signal_log`、`task_run`、`pipeline_run` |

## 3. 必须先解决的 7 个矛盾（否则解耦无从谈起）

| # | 矛盾 | 现状 | 解耦时的处理 |
|---|---|---|---|
| 1 | **行情同一对象多份存储** | 同一段 FG 行情同时存在于 `fut_kline` / `bar_15m` / `daily_bar` / `hourly_bar` / `main_continuous` | L2 建立**口径注册表**（caliber registry），明确"哪个用途用哪份"，上层只能按用途名取，不能按表名取 |
| 2 | **双 symbol 命名空间** | `FG888`（主连）vs `KQ.m@CZCE.FG`（天勤原生），`KQ.m@CZCE.FG` 已实测残留 18,866 行 | L2 统一出口：对外只暴露一种 code，内部映射；禁止上层拼接 symbol |
| 3 | **未复权 vs 复权口径混用** | PRD 规定回测用 `continuous`、统计用 `cont_adj`，但代码里两口径混读 | L2 接口强制参数化 `caliber='continuous'\|'cont_adj'`，缺参报错 |
| 4 | **本地容器连云端库** | `DATABASE_URL` 覆盖 `POSTGRES_HOST` | 解耦前先定死：本地=本地库，云端=云端库；compose 各自闭环 |
| 5 | **复权脚本不在镜像** | `runtime/_adjust_bars.py` 被 `.dockerignore` 排除却被 scheduler 调用 | L2 层重建时，复权必须进 `app/data/`，随镜像发布 |
| 6 | **回测两套** | M4（模型准确率，日线）vs bt_engine_min15（策略盈亏，15m） | L4 明确两个子模块：`model_eval`（M4）与 `strategy_backtest`（策略），各自独立指标，不混用 |
| 7 | **A 隐秘数轴与融合策略对立** | 一个是区间回归（15m），一个是趋势跟踪（小时线）；本轮实测叠加会互相稀释 | L5 设为**两个并列策略实例**，各自独立状态机与闸门，只在 L6 组合层做资金分配，**不共享信号** |

## 6. 验收口径（每层一条硬指标）

| 层 | 硬指标 |
|---|---|
| L1 采集 | 任一数据源失败不影响其他源；断点可续；写入幂等 |
| L2 数据 | 上层代码库中 `FROM bar_*\|fut_kline\|daily_bar\|hourly_bar` 出现次数 = **0** |
| L3 因子 | `available_at` 全覆盖；T 日数据不会出现在 T 日及之前的可用集合（自动断言） |
| L4 回测 | 任一策略变体可一键跑完"等权净值 + 六项稳健性 + 走前 + 容量梯度"并出报告 |
| L5 策略 | 策略模块零 DB 依赖；实时与回测信号逐笔一致（`accept_v34.py` 类锚点常绿） |
| L6 应用 | 页面只读接口；推送与信号解耦；web 单一来源 |
