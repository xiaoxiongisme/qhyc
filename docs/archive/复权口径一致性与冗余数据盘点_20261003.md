## 一、★★ 先修正我上一轮的两处口径结论

上一轮我说"PRD 指定 cont_adj、我用了 continuous 是替代方案"。**这个说法不完整，查 `app/data/caliber.py` 后必须修正**：

### ① 项目权威口径是 `back_adj`（等差后复权），不是我说的 continuous

`app/data/caliber.py` 是项目口径注册表（文件头注释：「本模块把『周期 × 口径 → 具体表』的映射固化成**唯一权威**，上层只能通过 `BarStore` 取数，禁止裸 SQL」）。

```python
#: 回测与对账的默认口径
#: 2026-09-30 用户拍板：**改用等差后复权**。
#: 依据（84 品种实测）：前复权 13 个品种历史价转负、且每次换月需全历史重写；
#:   等差后复权把负价降到 3 个品种、ATR 零失真、且**只追加不必重算**。
DEFAULT_CALIBER = "back_adj"

CALIBERS = ("continuous", "back_adj", "cont_adj", "contract")
```

`app/data/back_adjust.py` 口径要点：
- 后复权**锚定最早段**（最早段 `cum_offset=0`，历史价即真实价）
- 使跨换月的**点数差**归零
- **禁用等比**：实测 84 品种等比会让 87.8%~90.2% 品种的 ATR 失真，直接摧毁 2×ATR 止损 / 0.5×ATR 保本
- 仍可能有负价：长期 contango 品种后期段（实测 RU/FB/JD 三品种）

### ② cont_adj 早已被项目正式废弃（不是我新发现的）

`app/data/caliber.py` 第 30 行 + `scripts/deprecate_cont_adj.py` 文件头（2026-09-30）：

```
#:   cont_adj（加法前复权）因会产生负价（I888 最低 −1058.5，51.4% bar 为负）被废弃。
```

`ROUTES` 中 5 条 cont_adj 路由全部标注 `DEPRECATED 前复权：会产生负价且须全量重算`。

**我上一轮说"PRD §4.3.5 第 4 条指定 cont_adj"是对的，但漏了 `caliber.py` 这个更新的权威文件。** PRD 是 09-30 之前拍的，`caliber.py` 是 09-30 之后的修正，两者冲突时以 `caliber.py` 为准。

## 二、核心问题：我的回测口径是否合规？—— ✅ 合规，且是唯一可行

### 我的 daily/hourly 回测读 `fut_kline kind='continuous'`

**与官方验收脚本完全一致**：

```python
# scripts/accept_v34.py:50,61
"SELECT count(*) FROM fut_kline WHERE freq='hourly' AND kind='continuous' ..."
"SELECT trade_datetime, open, high, low, close FROM fut_kline
 WHERE freq=:f AND kind=:k AND symbol=:s ORDER BY trade_datetime ASC"
```

→ 我六轮验证与官方 `accept_v34.py` 读**同一张表、同一 kind**，基线可比。

### 但 `back_adj` 在 daily/hourly 上根本不存在

`roll_segment`（back_adj 的核心资产）实测覆盖：

| freq | 段数 | 品种数 | 覆盖起 | 覆盖止 | `cum_offset≠0` 段 | `price_shift≠0` 段 |
|---|---|---|---|---|---|---|
| min5 | 2,911 | 84 | 2015-01-05 | **2026-02-12** | 2,826 | 0 |
| min15 | 2,914 | 84 | 2015-01-05 | **2026-02-24** | 2,829 | 0 |
| min30 | 2,911 | 84 | 2015-01-05 | 2026-02-24 | 2,826 | 0 |
| min60 | 2,909 | 84 | 2015-01-05 | 2026-02-24 | 2,824 | 0 |

**只有 5/15/30/60 分钟，没有 daily 和 hourly。**

→ 结论：**我的 daily / hourly 回测只能用 `continuous`，这不是"我选择了它"，而是 back_adj 在这两个周期上无数据可用。**
→ 六轮验证的口径**无需推翻**，但必须在报告中标注为"受 back_adj 覆盖限制的过渡口径"。

### ★★ 删除前必须知道的三个阻断点

| # | 阻断点 | 证据 | 后果 |
|---|---|---|---|
| **1** | **删了会被自动重建** | `app/scheduler.py:920` — 05:00 重建作业「cont_adj←minute_bar_adj / continuous←bar_* / contract←contract_daily UPSERT」 | **只删数据无用**，必须先从 scheduler 摘掉 cont_adj 生成步骤 |
| **2** | 云端有独立数据 | 云端 `cont_adj` 1,012 万行，独立于本地 | 需本地+云端分别处理，且云端脚本需 `--i-know-production` |
| **3** | 备份未做 | 官方脚本只提示 `pg_dump` 不自动执行 | `fut_kline` 是超表（612 chunk），dump 耗时可能很长 |

### 我的建议：**可以删，但必须按"先断生成、再删数据、最后留备份"三步走**

**理由**：
1. 口径注册表已标 `DEPRECATED`，`DEFAULT_CALIBER` 已改为 `back_adj` —— 数据无正当用途
2. 15 个品种历史序列 100% 为负，**任何点数/幅度/ATR/止损分析都是垃圾**
3. 每日 02:30 曾有 `adjust_cont_adj` 作业，**现已停用**（scheduler.py:1211 打印 "adjust_cont_adj 停用"）→ 生产侧本已不依赖

**但必须先做**：
- [ ] 摘掉 scheduler 05:00 重建作业里的 cont_adj 生成步骤（否则删完立刻回来）
- [ ] `pg_dump` 备份（只 dump `kind='cont_adj'` 的行，或整表）
- [ ] 确认 `minute_bar_adj`（云端 9,289 MB）是否也要处理——它是 cont_adj 的**上游**，cont_adj 由它派生。上游留着的话，05:00 作业随时能再生成

**执行命令**（项目自带，安全设计）：

```bash
# 1. 先 dry-run（默认就是 report）
python scripts/deprecate_cont_adj.py

# 2. 本地删除
python scripts/deprecate_cont_adj.py --action delete --confirm

# 3. 云端删除（需双重确认）
python scripts/deprecate_cont_adj.py --env cloud --action delete --confirm --i-know-production
```

## 五、结论汇总

|---|---|

| 优先级 | 对象 | 建议 | 前置条件 |
|---|---|---|---|
| **P0** | `cont_adj` 994 万行（本地）+ 1,012 万行（云端） | ✅ **建议删** | ①先摘 scheduler 05:00 的 cont_adj 生成步骤 ②`pg_dump` 备份 ③决策 `minute_bar_adj`（云端 9.3 GB，上游） |
