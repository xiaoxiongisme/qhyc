## 一、核心发现：稳健性闸门差点做成"假闸门"

我第一版把它接在 `/fusion` 回测上（加 `BACKTEST_GATE_ENABLED` 开关）——**方向是错的**：

| | 融合引擎成交口径 | 闸门需要的口径 |
|---|---|---|
| 字段 | `entry_dt / exit_dt / entry_px / exit_px / pnl / side` | `R / risk / ep / xp / edt / xdt / dir / mult` |

**处置**：撤回错接，改接原生口径（`app/strategies/magic_axis.run_magic` 的输出与闸门需求

## 六、追加发现：`fut_kline` 重建 = 数据事故直通路径

`rebuild_fut_kline.py` 生产模式的执行顺序是 **先 DELETE、后取源**：

```sql
DELETE FROM fut_kline WHERE kind IN ('cont_adj','continuous')   -- 先删
SELECT distinct symbol FROM minute_bar_adj ...                   -- 后取源
```

源表一旦缺失/为空 ⇒ **删光再失败**，而且这两个 kind 就回不来了。

实测两端差异（本地与云端完全不同，切勿混淆）：

| 环境 | `minute_bar_adj` | `fut_kline` | cont_adj / continuous |
|---|---|---|---|
| 云端 | **57,652,640 行** | 26,115,812 | 9,978,431 / 9,942,397（合计 ≈ 1,992 万行） |
| 本地 | **表不存在** | 26,115,812 | — |

雪上加霜的是：`FutKlineRebuildConfig.enabled` **默认 True**，而开关为 True 时
旧的 `adjust_cont_adj`（02:30）**不再注册**——即这条链路此前一直没被维护，
修好 `subprocess` 后又**会真的开始跑**。

**处置**：守卫加在**破坏点之前**，而不是在调用方兜异常。
1. 脚本内：DELETE 之前校验源表存在且非空，不满足即 `return 2`；
2. 调度侧：调起脚本前查 `to_regclass('minute_bar_adj')`，缺失则 ERROR 跳过。

实测：本地 `--dry-run` → `[abort] 源表 minute_bar_adj 不存在 —— 拒绝执行`；
直接调用 `_rebuild_fut_kline_job()` → ERROR 日志，且 `fut_kline` 仍 **26,115,812 行未被删**。
提交 `a06f6bb`（已 push）。

> 通用纪律：凡是 `DELETE/TRUNCATE` 在取源之前的批处理，必须在删除前校验源就绪。
> 否则失败模式不是报错，而是**数据被清空**。

**顺带**：`_spot_basis_job` 经 `_dt` 修复后本地试跑**成功**（`rows=108`，约 2 秒），
证实此前从未跑通过——与"spot_basis 仅 8 天"的数据缺口完全互证。

## 七、云端上线前必须拍板（当前阻塞）

1. **`rebuild_fut_kline` 的耗时必须先测出来**：本地**无源表，无法试跑**（这是你选的"先本地试跑"
   路线走不通的唯一原因）。建议**在云端跑 `--dry-run`**——它只建 `fut_kline_drv` 临时表、
   **不碰生产 `fut_kline`**——测出真实耗时再决定是否放开 05:00 作业。
   否则 `timeout_sec=7200` 一旦超时，就是在**已经 DELETE 之后**失败。
2. **云端 API 绑 `127.0.0.1` 会切断外部直连看板**：云端 compose **没有反向代理**。
   三选一：保留环回 + `ssh -L` / 加反向代理 / 改回 `0.0.0.0` 但同时填真 key。
3. **填真 key 会让看板回测页 403**：`web/src/api.jsx` 的 `postJSON` **不带 `X-API-Key`**，
   而看板会 POST `/backtest/fusion`、`/backtest/fusion/matrix`。
4. **要不要顺带启用 `_spot_basis_job`**：此前 `enabled=false`，修复后启用才会补基差数据。
