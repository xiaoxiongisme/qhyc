## 二、最严重的 6 个问题（按优先级）

### P0-1 · 复权脚本不在镜像里 → 云端复权每天静默失败

`app/scheduler.py` 定时调用 `runtime/_adjust_bars.py`（02:30）与 `runtime/_adjust_minute.py`（04:30）；但 `.dockerignore` 明确排除 `runtime`，云端 `runtime` 又是空 named volume → **文件不存在，作业打一条"找不到脚本"日志就返回，不报错**。
同类：`scripts/rebuild_fut_kline.py`、`scripts/sync_cloud_local.py`、`scripts/compute_factor_value.py` 等 **8 个生产脚本从未提交 git**，同样不在镜像里。

### P0-2 · 配置文件被 gitignore，镜像配置不可复现

`config/local.yaml`、`config/cloud.yaml` 被 `.gitignore` 排除（`git ls-files config` 只剩 `transmission_config.yaml`）。`Dockerfile` 的 `COPY config ./config` 只在"构建机上恰好存在这两个未入库文件"时才生效 → **换台机器 build 出来的镜像没有品种池、没有融合参数**。

### P0-3 · 本地容器实际连的是云端库

`docker-compose.yml` 同时设了 `POSTGRES_HOST=timescaledb` 和 `DATABASE_URL=...@host.docker.internal:15432`；`app/core/config.py:72` 里 **`DATABASE_URL` 优先** → 本地 api/scheduler/pipeline 全部写云端。本地 `qhyc-timescaledb` 实际只服务裸机脚本。`POSTGRES_HOST` 是死配置。

> **⚠️ 勘误（2026-10-01 实测，本节结论已失效）**：`docker-compose.yml` 现在**不含 `DATABASE_URL`**（api/scheduler/pipeline 三处均仅 `POSTGRES_HOST: timescaledb`）；容器内 `printenv DATABASE_URL` 为空，`get_engine()` 实测指向本地 `timescaledb:5432` —— **本地容器读写的全部是本地库**（2026-10-01 的 82 品种补采数据均落在本地，云端零写入）。P0-4「双端对同一云端库双跑」的风险随之不成立（本地写本地、云端写云端，除非云端 compose 另设 DATABASE_URL）。`DATABASE_URL→host.docker.internal:15432` 何时被移除待考。云端库水位与采集状态仍需 SSH 隧道（本机 15432 当前 CLOSED）才能核实。

### P0-4 · 本地与云端 scheduler 可能对同一库双跑

两端 scheduler 若同时 Up，会对**同一个云端库**执行同一批任务：`fusion_scan` 重复推送、`minute_and_bars` 并发"尾删再重建"互相破坏。本地 compose 未设 `CLOUD_SYNC_ENABLED=1`（该开关本就是为"裸机只跑同步"设计的）。
**需你在服务器 `docker ps` 复核云端容器状态。**

### P0-5 · 云端代码与 git 已分叉

`scripts/_patch_minute.py`、`_patch_minute2.py`、`_patch_inventory.py` 是**直接改云端容器内源码**的补丁脚本。云端跑的代码 ≠ git 里的代码。

### P0-6 · 云端合成作业与复权作业竞态

云端 `bar_*` 合成作业**周期性"尾删再重建"**；复权作业撞上就读到被删尾的源，静默产出"缺最近几天"的 `cont_adj`。本轮实测：17:20 跑 min30 只写到 09-19；17:30 重跑到 09-24；17:38 再查源又被清空。

## 三、结构性缺陷（不是 bug，是设计债）

| # | 缺陷 | 证据 |
|---|---|---|
| D1 | **零业务外键**，关联全靠列名约定 | `pg_constraint` 只有 `_timescaledb_*` |
| D2 | **行情同一对象多份存储** | 一段 FG 行情同时存在于 `fut_kline`/`bar_15m`/`daily_bar`/`hourly_bar`/`main_continuous` |
| D3 | **双 symbol 命名空间** | `FG888` vs `KQ.m@CZCE.FG`（已实测残留 18,866 行，云地各一份） |
| D4 | **两套回测并存且口径不通** | M4（日线模型准确率）vs bt_engine_min15（15m 策略盈亏） |
| D5 | **云地数据库严重分叉** | 本地无 1m/5m；`fut_kline` min15 continuous 本地 1 符号 vs 云端 84；min30/60 continuous 本地**完全缺失** |
| D6 | **基本面远不达 PRD** | `spot_basis` 432 行（要求 ≥2000 日）、`member_position_rank` 本地仅到 2023、`roll_yield` 本地 0 行 |
| D7 | **因子库"实现了没接线"** | `asof.py` 已实现 T2/T3/T5/T6，但计算未进调度、注册表仅 11 条（在产 19 个） |
| D8 | **前端"已开发未部署"** | 源码在 git，compose 无 web 服务，dist 双来源（镜像 + 本地挂载） |

## 四、六层解耦的一句话路线

> **先止血（Phase 0：把缺失脚本/配置补进 git、定死云地连接、消双跑），再立 L2 数据层（Phase 1：插入 BarStore，禁上层裸 SQL），其余分层都是这一个动作的展开。**

| 阶段 | 内容 | 产出 |
|:--:|---|---|
| Phase 0 | 止血：补齐 git、修配置、消双跑、修竞态 | 系统可从 git 全新构建并跑起来 |
| Phase 1 | 立 L2 数据层（BarStore + 口径注册表 + 单 symbol 出口） | 上层零行情裸 SQL |
| Phase 2 | 策略层纯函数化（因子改为注入；A 隐秘数轴并列独立） | 策略模块零 DB 依赖 |
| Phase 3 | 回测层独立（model_eval / strategy 两个子模块 + 稳健性套件） | 一键出全套回测报告 |
| Phase 4 | 因子层接线（进调度 + 补注册表 + 准入校验） | 因子每日自动更新并注入策略 |
| Phase 5 | 应用层前后端分离（聚合 SQL 下沉、web 单一来源、推送解耦） | 页面只读、推送与信号解耦 |
