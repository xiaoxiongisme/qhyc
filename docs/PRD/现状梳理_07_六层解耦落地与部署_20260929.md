## 4. 可扩展：后续如何增删因子 / 策略

**加一个因子（4 步）**
1. 写计算脚本（幂等 upsert → `factor_value`，照抄 `compute_factor_v1v6.py`）；
2. `factor_registry` 插一行（`enabled=false, default_weight=0, max_weight ≤ 0.05`）；
3. `python scripts/admit_factors.py --factors <id> --apply` 跑六道闸门；
4. 通过后把 `default_weight` 调到目标值；`max_weight` 之和须 ≤ 1.0。

**加/减一个因子（运维）**：改 `factor_registry.enabled` 即可；
`enabled=false` 走恒等路径（T18 双向等价，回归待补）。

**加一个策略**：`app/strategies/registry.py` 里加一条 `StrategySpec`
（`key/freq/caliber/fn/default_params/enabled`），或运行时 `register(...)`；
再在取数时用 `app.data.load(symbol, freq, caliber)` 保证口径唯一。

**加一个数据口径**：`app/data/caliber.py` 的 `ROUTES[(freq, caliber)]` 登记；
未登记即抛 `CaliberError` —— 防止"随手换表"造成跨表口径漂移。

### 8.4 同步链路两个结构性缺陷（2026-09-29 实测发现，已修）

排查"为什么同步了还落后"时发现，纯水位增量有两类补不回来 / 会倒退的问题：

**① 云端往历史回补 → 本地产生「永久分歧」（已修：回看窗口重放）**
云端分钟线是"尾部重算 + 回补"语义：`adjust_minute` 每次重建会把过去 N 天整段重算，
并把原本缺失的**旧日期行**补进去；而增量只拉 `> watermark` 的行，云端补到水位**之前**的
行永远同步不到。实测 `bar_60m` 差 **3,205 行，全部落在 2026-09**（云端回补窗口内），
`bar_30m` 09-22 当天本地只有 31 行而云端 763 行。
→ 新增 `--lookback-days`（默认 **30**，调度侧 `CLOUD_SYNC_LOOKBACK_DAYS`）：
增量时把 `[now-30d, wm]` 一起重放（先删后拷，幂等）。代价仅几千~几万行。

**② 源端重建期间同步 → 把本地「回滚」（已修：源端回退守卫）**
云端重建是"先删尾部再重算"，过程中源表 `max(bucket)` **先变小后变大**。此时同步会把
本地整段尾部删成云端的中间态 —— 实测 `bar_30m` 被回滚 7 天
（4,883,649→4,880,860，水位 09-29→09-22），**不报错、无人察觉**。
→ 新增守卫：源端 `max < watermark` 即判定"源在重建/异常"，**直接中止不动本地**
（`[ABORT] src max ... < watermark ...`），确需覆盖才加 `--force-regressed-src`。
同时把单表失败改为跳过而非中断整批。

**③ 顺带修的隐患**：`_env_dsn()` 只认 `{prefix}PGPASSWORD`，而 compose 里写的是
`{prefix}PGPWD` → 一旦 `.env` 改口令，云地同步会**静默回落默认口令**并连库失败。
现两个名字都认。
