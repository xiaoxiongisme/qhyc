# 数据层 PRD · 专业评审与疏漏补强清单

> 评审对象：`量化系统-数据层PRD.md`（v1.4，2026-10-03）
> 评审视角：架构实现 / 逻辑合理性 / 性能 / 健壮性 / 可拓展性 / 测试与可观测性
> 评审结论用途：**全部发现交由 CodeBuddy（CB）改造时落地**，本文件是 PRD 的评审补强附录，不替代 PRD。
> 配套索引：PRD §14.4（G 系列改造点）+ PRD §15（评审结论）。

---

## 0. 总体结论（先讲结论）

PRD 的方向正确、拆解到位：**四模块分层 + 接口硬约束 + 单一 akshare 源 + 复权只存 offset + 双轨回测 + 成本单一真源（C8 校正）** 是成熟且自洽的顶层设计，且本轮回测已用真实管线实证了 offset 引擎正确、时区一致性无虞。

但作为一份"交 CB 改造的单一真源"，它在**工程落地的安全网**上仍有系统性疏漏，集中在五点：

1. **健壮性最大风险**：把 天勤 比对层（T7）摘掉、又只留 akshare 单一免费抓取源，等于在新架构里引入**单点依赖（SPOF）却未配套韧性层**——akshare 是爬虫源，必有限流/脏数据/偶发失败。
2. **逻辑最大风险**：**两套"换月"定义各自为政**（`main_contract_map.change_flag` 按合约符号变、`roll_segment` 按价格双门），在换月边界上信号（后复权）与执行（真实合约）可能错位。
3. **自相矛盾**：B9 把默认口径改成 `cont_adj`，但 B2 承认 `roll_segment` **缺日线/小时线段** → 默认 `cont_adj` 对日线/小时线会 fail-loud（B8），等于默认口径对"预测/回测默认日线源"先坏后修。
4. **数据正确性**：C1 选的日历源 `tool_trade_date_hist_sina` 是**股票**日历，期货有其专属作息（中金所 09:15 开盘、无夜盘、国债差异、节假日提前收盘），直接套用会系统性错。
5. **性能与落地保险缺失**：B8"运行时 as-of join 套 offset"在 10 年 × 84 品种 × 多周期回测下不可行；且"上层禁裸 SQL"等硬约束**只有验收口径、没有强制执行机制**。

以下按维度展开，每条标注 **发现 / 为何是疏漏 / 建议 / 严重度**，末尾给出建议 CB 落地的改造点（与 PRD §14.4 的 G 系列一一对应）。

## 1. 架构实现（Architecture）

### 1.1 【G9·P1】L0 边界被 `fut_kline.continuous` 击穿
- **发现**：§3/§5 定义 L0 = "只入库备份、不参与任何计算/合成/复权"，但 `fut_kline` 同时持有 `contract`（原始）与 `continuous`（拼接连续，是**派生品**）两种 kind；本轮回测确认 `continuous` 仍有 ~990 万行。
- **为何是疏漏**：一个"只存原始"的 L0 层里躺着派生连续序列，既模糊层边界，又让 B9 把默认口径切到 `cont_adj` 后，`continuous` 变成既冗余又易误用的"第三口径"。
- **建议**：明确 `fut_kline.continuous` 的归宿——要么迁到 L3 连续序列物化（与 `caliber_registry` 收口），要么在 B9 落地后**显式废弃该 kind**（写一次迁移 + 消费方清零）。同时在 §2/§5 把 L0 定义修正为"含原始合约棒，不含任何拼接/复权派生"。
- **严重度**：P1（口径分叉隐患，不阻塞但会反复咬人）。

### 1.2 【G7·P2】采集源未抽象成 Provider 接口，去天勤后失去"可重启第二源"的能力
- **发现**：§6.4 把 天勤 彻底删除（T1/T7/T9），且 §6.4.6 结论"不新增容器"。但采集器（`minute_collector`/`hourly_collector`/`contract_bars`）内部仍是"akshare 分支 + 已删的 天勤 分支"的硬编码结构，没有统一的 `BaseSource`（fetch_symbol / fetch_range / health）抽象。
- **为何是疏漏**：单一免费爬虫源 + 无抽象 = 一旦 akshare 接口变动/限流，只能改采集器代码；且未来想加交易所直连/付费源时须重构。与"可拓展性"目标相悖。
- **建议**：定义 `SourceProvider` 抽象（fetch / health / rate_limit_hint），akshare 作为唯一 enabled provider 实现；天勤 不删代码语义，仅标记为 `disabled` 而非物理移除，使"韧性第二源"可低成本复活（呼应 G1）。
- **严重度**：P2（架构整洁度，非阻塞）。

### 1.3 【G13·P2】`FundamentalsStore` 的 T+1 前视锁仅对回测，缺 `as_of` 模式
- **发现**：§8.2 `_lagged` 视图"T 日数据 T+1 才可读"是为回测防前视设计的，但实时预测/信号需要**当日**基本面。
- **为何是疏漏**：同一接口两种消费语义（回测禁前视 / 实盘要最新）没有区分参数，CB 落地时要么回测被锁死拿不到盘后数据，要么实盘误用未来值。
- **建议**：`FundamentalsStore.load(..., as_of='backtest'|'live')`，回测模式走 `_lagged`，实盘模式直读。
- **严重度**：P2。

### 1.4 【G11·P2】缺可观测性（observability）章节
- **发现**：全文无指标/监控设计。去掉 天勤 比对层后，如何知道"今日 84 品种 × N 周期是否都拉到了、延迟多少、roll_segment 重建耗时、offset 覆盖率"？
- **建议**：新增 §"可观测性"：每品种每周期 freshness 表 + 看板 + 告警；采集成功率/延迟 SLA；`roll_segment` 重建时长与段数漂移；offset 覆盖率（有段的 symbol×freq / 应有）。
- **严重度**：P2（运维可见性）。

### 1.5 架构上已经做对、应保留的
- 四模块 + 接口硬约束（§2/§8.2）方向正确；
- 单一 akshare 源 + 融入现有镜像（§6.4.6）决策合理，避免容器膨胀与版本漂移；
- 加法为主、开关单行回退、append_only 可裁剪（§11 原则）是稳健迁移策略。

## 2. 逻辑合理性（Logic）

### 2.1 【G2·P0】两套"换月"定义未对齐 —— 信号与执行在换月边界可能错位
- **发现**：`main_contract_map.change_flag`（§4.2/§6.5.2）= "与上一交易日 underlying 不同"（**按合约符号**）；`roll_segment`（§6.2，双门检测）= **按价格跳变**（振幅门 + 8888 比率门）。两者是**独立生成**的。
- **为何是疏漏**：若主力切换走"持仓量渐进交叉"（价格不跳），`change_flag` 触发但 `roll_segment` 不触发 → 回测执行序列换了合约，后复权序列却无 offset 边界 → 信号/执行在换月处对不齐；反之价格跳变但符号未变（极少见）亦然。**这是回测"信号-执行"一致性的根因级漏洞**，比 B4/B5 的"双轨"设计更底层。
- **建议**：**以 `main_contract_map` 的 change 点为换月事件的唯一真源**，`roll_segment` 由 change 点派生 offset；双门/8888 比率门降级为"校验/告警"（发现 price 跳变但无 change 点 → 标记异常，而非自作主张造 offset）。这样信号与执行天然同源。
- **严重度**：**P0（阻塞 B4/B5/B9 的正确性）**。

### 2.2 【G3·P0】B9 默认 `cont_adj` 与 B2"缺日/小时段"自相矛盾
- **发现**：B9 定 `caliber_registry` 默认 = `cont_adj`，`BarStore.load` 缺省返回后复权；但 B2 明确" `roll_segment` 现状仅 min5/15/30/60，**缺日线/小时线**"。而 §5.1 写明 `daily_bar` 是"预测/回测默认日线源"。
- **为何是疏漏**：B9 生效后，任意 `BarStore.load('FG','1d',cont_adj)` 会因无日线段触发 B8 的 fail-loud → **默认口径对自身最重要的日线源先坏**；或 CB 被迫在 B2 完成前临时回退默认，造成"拍板了却没生效"的半成品。
- **建议**：在 B9 与 B2 之间加**显式先后约束**：B2 的 `daily/hourly` 段必须**先于**默认口径切换生效；或 B9 做成"按 freq 渐进"——仅对已构建 offset 的 freq 默认 `cont_adj`，其余 freq 显式 fallback 并告警（不得静默返回 raw）。须写进 §10 验收。
- **严重度**：**P0（拍板项的落地顺序陷阱）**。

### 2.3 【G10·P2】`--positivity` 平移是"治标"，且引入层级不连续风险
- **发现**：§12/R12 把 6 个 backwardation 品种负价当作"缺陷"，靠 `--positivity` 加全局常数抬升消除，并称"点数/MA/ATR 信号不受影响"。
- **为何是疏漏**：① 平移改变历史各段**绝对价位层级**，对任何**绝对价逻辑**（按价格水平的仓位尺度、tick 价值、与固定阈值的比较）会引入段间不连续；② 后复权空间出现负价本身对**收益率类**指标（差值/差之比）其实无害——真正要防的是 RSI/随机等**价格比值**类指标，而它们用的是价差与价差之比，并非价格水平。
- **建议**：**不必强制 positivity**；改为：在指标层对"价格水平比值"类运算做非负保护，并保留一个"锚段偏移使最小价≥0"的**可选项**（默认关）。若保留 `--positivity`，须在 `roll_segment` 记录所用常数，保证重跑一致（见 G-算法版本化）。
- **严重度**：P2（认知校正，非阻塞）。

### 2.4 【G10·P1】B6"长周期收益回真实合约空间"缺数据源定义
- **发现**：B6 要求 250 日动量/年化在真实合约空间算，但 PRD 未说明该"真实合约空间收益"从哪取——`BarStore.load(caliber='contract')`？还是 `main_contract_map` + `daily_bar` 拼接？
- **建议**：明确 B6 的数据路径（建议：`BarStore.load(symbol, '1d', caliber='contract')` 经 `main_contract_map` 逐合约取真实日收益，换月处桥接不计收益），写进 §8.2 接口契约，避免 CB 各自实现。
- **严重度**：P1（落地口径空白）。

### 2.5 【G4·P1】C1 日历源选型错误（股票日历套期货）
- **发现**：C1 指定 akshare 源 `tool_trade_date_hist_sina()`（**股票**交易日历）+ `option_trade_time_em()`（**期权**交易时间）。但期货作息与股票不同：中金所 09:15 开盘（非 09:00）、国债/股指**无夜盘**、节假日**提前收盘/无夜盘**、各所夜盘时段不一（见 akshare 期货交易时间表）。
- **为何是疏漏**：用股票日历做期货"可交易时间/下一交易日/交割月第 N 交易日"判定，会在中金所、国债、节假日前后系统性偏差，直接污染 C2 护栏与 C7 门禁的时间边界。
- **建议**：改用 **akshare 期货专属日历** —— `futures_rule(trade_date)`（国泰君安期货，按日返回各所各品种日历 + **保证金比例**，同时喂 C6 风控窗口）或交易所官方日历；日盘/夜盘时段用 `futures_trading_time`。`tool_trade_date_hist_sina` 仅作"全市场是否开市"的粗校验。此点已实测确认（搜索 akshare 期货文档）。
- **严重度**：**P1（数据正确性，C1 必须改源）**。

## 3. 性能（Performance）

### 3.1 【G5·P1】B8"运行时 as-of join 套 offset"不可规模化
- **发现**：B8/§8.2 要求 `BarStore.load` 每次返回后复权序列时**运行时**套 `roll_segment` offset（as-of join）。回测要扫 10 年 × 84 品种 × 多周期，每次调用都重算 join。
- **为何是疏漏**：回测引擎逐 bar/逐品种调用 `load` 时，重复 as-of join 是 O(N·segments) 且无法利用索引；实测 84 品种 2830 换月点虽小，但乘上回测重复调用会成倍放大。B9 默认 `cont_adj` 后此路径成为热路径，性能必崩。
- **建议**：**决策二选一并写进 §6.2/§8.2**：
  - 方案 A（推荐）：每次 `roll_segment` 重建后**物化** `bar_*_adj` 后复权表（raw `bar_*`  immutable，adjusted 由重建作业刷新），回测读物化表；仅在两重建之间存在"最多一日"的微滞后，对回测无影响；
  - 方案 B：保留运行时套用，但加**进程内/Redis 缓存**（按 symbol×freq×caliber 缓存已套 offset 的序列，TTL 绑定重建时间戳）。
  - 并给出性能目标（如单品种 10 年 15m 加载 < 200ms）。
- **严重度**：**P1（B9 落地前置）**。

### 3.2 【G6·P1】`sp_build_l*` 重建的并发与幂等
- **发现**：`sp_build_l2_roll_segment` 标 append_only，但未规定"重跑是否幂等"（按 `max(seg_id)` 跳过已建段？）；`sp_build_l1_*` 标 add_modify_only（UPSERT）但未规定"全量重建时是否锁表/阻塞读"。
- **为何是疏漏**：每日调度的重建若全量重写 `bar_15m`（千万级），会锁表、阻塞回测/API 读；`roll_segment` 重跑若不复幂等会**重复造段**。
- **建议**：① `roll_segment` 重建加"已存在 seg 跳过"幂等守卫；② L1/L2 重建走**临时表→原子 rename/swap**，读方零阻塞；③ 明确 chunk 策略（TimescaleDB `segmentby=symbol`、`time_bucket` 压缩）。
- **严重度**：P1。

### 3.3 缺 TimescaleDB 超表/压缩策略
- **发现**：`bar_5m` 已 2462 万行，`minute_bar` 未来若补（虽 R5 暂缓）将数亿行。`bar_*` 是否 hypertable、`segmentby`/压缩策略未规定（仅 §9 提过 `max_locks_per_transaction` 的坑）。
- **建议**：§9 补"所有 `bar_*` 为 TimescaleDB 超表，`segmentby=(symbol)`、按时间压缩（如 7d 以上 compress），`roll_segment` 小表常规表"。
- **严重度**：P2。

## 4. 健壮性（Robustness）—— 本评审最重点关注

### 4.1 【G1·P0】单一免费爬虫源 = 单点依赖，且 T7 摘掉了唯一比对层
- **发现**：§6.4 决策"只留 akshare"且 T7 删 `天勤_calibrator` 双源比对与 `accept_天勤` 分支。akshare 是**爬取 sina/东财等公开页面的免费库**，必然有：限流、偶发返回脏数据/空、接口变更、盘中数据延迟。
- **为何是疏漏**：原系统好歹有 天勤 兜底与双源比对；新架构在"更不可靠的单源"上**反而移除了保险**，且 §6.4.6 反对加容器使"加一个稳定第二源"也变难。**这是把系统可用性赌在爬虫稳定性上**。
- **建议**（落地韧性层，交给 CB）：
  1. **采集框架内置韧性**：指数退避重试 + 断路器 + 本地磁盘缓存（上次成功结果，TTL 内降级用）+ 限流（尊重 akshare 节奏）；
  2. **新鲜度 SLA + 告警**：每品种每周期 freshness 表，超阈值告警（见 G11）；
  3. **保留"比对"精神但不绑定 天勤**：用"与上一成功批次的价差/突变一致性"做自动校验（脏数据拦截），而非依赖第二数据源；若必须第二源，按 G7 的 Provider 抽象接交易所/东财官方 API；
  4. **部分失败不静默**：某品种拉取失败 → 记 `anomaly_ticket` + 告警，绝不空过（对照 B3/T2 的"静默失败"教训）。
- **严重度**：**P0（去天勤决策的配套，不可省）**。

### 4.2 静默失败模式散布，缺统一失败/告警策略
- **发现**：B3（`adj` 假列静默取 0 行）、T2（job 变 no-op 静默）、`_fetch_akshare` 返回 `[]` 静默、B8"缺口 fail-loud"但**未定义 fail 的方式与告警通道**。
- **建议**：§12 单列"失败语义规范"：区分 fail-loud（抛异常 + 告警 + 阻断下游）vs fail-soft（记 ticket + 降级 + 告警）；所有采集/重建作业统一接入告警，杜绝"跑完了但其实是空"的假象。
- **严重度**：P1。

### 4.3 【G6·P1】`roll_segment` 重建幂等（见 3.2）
（同 3.2，不重复）

### 4.4 C2 护栏规则改动未声明"历史回算"影响
- **发现**：C2 改 `_last_trading_day` 用真实日历，但历史回测的护栏也跟着变；PRD 未要求"用官方日历对历史 `main_contract_map`/护栏**回溯重算**"。
- **建议**：C2 落地时跑一次历史回溯重建（官方日历下重算交割月护栏与可交易性），并作为 §10 验收项。
- **严重度**：P1（可复现性）。

### 4.5 双门漏检/误检的兜底不足
- **发现**：§6.2 双门减少假盈亏，但**漏检**（真实换月 gap 低于振幅门）会在后复权序列留下未抵消的真跳变 → 假盈亏；**误检**（真实市场隔夜涨跌停 gap 被当换月）会造错误 offset。
- **建议**：用 8888 指数连做**系统性对账**（B7 升级为"每日自动扫：有价格跳变却无换月点 / 有换月点却无价格跳变 → 标记 anomaly"），而非仅靠人工质量门控。
- **严重度**：P1。

## 5. 可拓展性（Extensibility）

### 5.1 【G7·P2】采集源 Provider 抽象（见 1.2）
### 5.2 周期（freq）以"表名"承载，新增周期成本高
- **发现**：`bar_5m/15m/30m/60m` 各一张表，新增周期（2m/4h/日）需新建表 + 新 `sp` + 新 `roll_segment(freq)`。
- **建议**：评估改为单表 `bar(freq, symbol, ts)` + check 约束 + 按 freq 的 chunk/压缩策略；至少 §9 注明"新增周期的标准步骤"，使扩展有章法。
- **严重度**：P2。

### 5.3 `caliber_registry` 仅映射表，不编码 transform
- **发现**：注册表 (table, caliber, usage) 只指向"哪张表"，但新口径（如量加权连续、分红调整）需要不同 transform，注册表无法表达。
- **建议**：注册表增加 `transform_ref`（指向 `sp`/函数名），使"加新口径 = 插一行 + 注册一个 transform"，真正达成口径可插拔。
- **严重度**：P2。

### 5.4 【G11·P2】新增品种的自动化接入
- **发现**：`contract_code_map` 需 `--rebuild-map` 收尾（§3.3/§4.3），新交易所需改代码（sessions/calendar）。
- **建议**：新期货品种（同所内）应全自动（从 akshare 拉清单→dim 回填）；仅"新交易所/新资产类"才需代码，写进 §4。
- **严重度**：P2。

## 6. 测试与验收（Quality / Testability）—— 落地保险

### 6.1 【G8·P1】"硬约束"只有验收口径，无强制执行
- **发现**：§10 把"上层裸 `FROM bar_*` = 0""接口仅 BarStore"作为验收，但无 **CI 门禁**（grep/AST lint 拦截裸表引用）、无 `lint_direct_table_refs` 是否进 CI 的说明、无回归测试。
- **建议**：① 把 `lint_direct_table_refs` 纳入 CI/pre-commit 强制；② 单元测试：`symbol_code` 归一、cost `on_date`、夜盘归属、`back_adjust` 抵消（用已知换月样本）；③ **Golden Dataset + 回归**：固定种子→固定数据，任何重构后跑对拍，差异须解释；④ B8/B9 的 fail-loud 须有"offset 缺口时抛指定异常"的测试。
- **严重度**：**P1（没有门禁，硬约束会随时间腐烂）**。

### 6.2 缺数据质量测试套件
- **发现**：OHLC 逻辑（高≥max(o,c) 等）、无缺失、无重复、复权 A/B 对拍，仅散见描述，未形成可跑套件与 §10 勾选项。
- **建议**：形成 `tests/data_quality/` 套件，每次重建后跑，失败阻断发布。
- **严重度**：P2。

### 6.3 复权/换月算法未版本化（可复现性）
- **发现**：C3 版本化了"主力切换规则"，但**换月检测（双门阈值/比率门 0.40）与 positivity 选项**是代码常量，改阈值会无声改变历史 offset → 历史回测不可复现。
- **建议**：`roll_segment` 增加 `rule_version`（或全局 `adjustment_config` 快照），每重建记录所用版本；回测可断言数据由哪个版本生成（呼应"防不可复现三问"）。
- **严重度**：P2。
